# Contributing

Skrapa is self-hosted: its own docs site (`web/`) is a Skrapa site built with the Skrapa CLI (`src/bin/`), and the CLI itself is a TypeScript project compiled and bundled into a single `bin/index.js`.

## Layout

- `src/bin/` is the CLI source: `index.ts` (entry and command dispatch), one `cmd-*.ts` per command (`cmd-build.ts`, `cmd-dev.ts`, `cmd-fix.ts`, `cmd-init.ts`, `cmd-page.ts`), and the shared modules they build on (`config.ts` for reading the `skrapa` key of `tsconfig.json` and the flag precedence over it, `jsx.ts` for the build-time JSX runtime, `bundle.ts` for the CommonJS bundler, `format-html.ts` for the dev-only pretty printer, `tag-parser.ts` and `rewrite-shell-imports.ts` for the tag machinery, `output-paths.ts` and `link-check.ts` for the checks on the output tree, `utils.ts`, `types.d.ts`).
- `src/scripts/` holds maintainer-only scripts (not shipped) that drive local dev, testing and packaging.
- `src/tsconfig.json` compiles both of those. It is rooted at the repo (`rootDir: ".."`, `outDir: "../.skrapa"`, `include` of `**/*.ts` and `../skrapa.d.ts`), so the CLI entry compiles to `.skrapa/src/bin/index.js`. There is no `tsconfig.json` at the repo root.
- `web/` is the docs site. It is a skrapa root whose project root is the repo root: `web/tsconfig.json` carries its `skrapa` key (`"output": "../dist"`, port 8090, host `localhost`, origin `https://skrapa.localhost`, `"projectRoot": "../"`) and includes `../skrapa.d.ts`. Beside it are `web/index.tsx`, `web/about/`, `web/docs/`, `web/components/`, `web/site.ts` (the production origin and other site facts) and `web/assets/` (`CNAME`, `robots.txt`, the generated `sitemap.xml`, `og.png`, `style.css`).
- `skrapa.d.ts` at the repo root is the source of truth for the global types. It ships in the package, every build copies it into the project root of the site being built, and `template/skrapa.d.ts` has to stay byte-identical to it (`cp skrapa.d.ts template/skrapa.d.ts`).
- `template/` is the scaffold `skrapa init` copies into new projects: the pages and `tsconfig.json` in `template/src/` (its skrapa root), with `assets/`, `README.md`, `skrapa.d.ts` and `.github/workflows/skrapa-pages.yml` beside it.
- `.skrapa/` is temporary `tsc` output, mirroring the source tree. At the repo root it holds the CLI and scripts: `npm run build` removes it when it finishes and `npm run dev` when it stops (`npm run test:unit` rebuilds it and leaves it). In `web/.skrapa/` it holds the site, and the CLI removes it after a build and when its dev server stops. Never shipped.
- `bin/index.js` is the CLI, bundled from `.skrapa/src/bin/index.js` and everything it `require`s (see `src/bin/bundle.ts`) into one file with no relative-`require` dependencies on its siblings, since only `bin/`, `template/` and `skrapa.d.ts` ship in the published package.

## Scripts

| Script | What it does |
| --- | --- |
| `npm run build` | Regenerates `web/assets/sitemap.xml` from the pages under `web/` (`src/scripts/sitemap.ts`; commit it when it changes, a unit test fails if it is behind), compiles the CLI and scripts (`tsc -p src/tsconfig.json`), bundles `.skrapa/src/bin/index.js` into `bin/index.js`, then runs that freshly built CLI from `web/` (`node <repo>/bin/index.js build`) to produce the docs site in `dist/` at the repo root. Invoked by path, never as `npx skrapa`: `npx` resolves through the global bin, so a missing or stale `npm link` would silently build this site with the *published* skrapa and still go green. Nothing here touches the global link; `npm run dev` and `test:e2e` do that. Bare `npx skrapa` at the repo root does not scaffold either, since the root has a `package.json`. |
| `npm run og-image` | Re-renders `web/assets/og.png`, the social card every page's `og:image` points at, by screenshotting a small HTML card in headless Chrome (`src/scripts/og-image.ts`; set `CHROME=` to point at a browser it does not find). Run it when the tagline or brand colours change and commit the PNG. Deliberately not part of `build`, so the build never needs a browser. |
| `npm run dev` | Runs `npm run build` once and `npm link`s the checkout (so the `npx skrapa` calls below resolve here), then starts two dev servers in parallel: one in `web/` for the docs site (port 8090), and one for a project freshly scaffolded into `.tmp/project/` with `npx skrapa init --new --no-dev`, served from its skrapa root `.tmp/project/src/` (port 8080). Each is logged with a colored `[web]`/`[tmp]` prefix. Watches `src/bin/**`: rebuilds the CLI and restarts both servers. Watches `template/**`: rescaffolds `.tmp/project/` and restarts its server. Each server runs in a process group of its own. Ctrl+C, closing the terminal, or a SIGTERM stops every group and removes the global link (`npm unlink -g skrapa`), so `npx skrapa` in other projects goes back to the published package. If the script crashes instead, the servers are killed outright and the link stays, so unlink it by hand. Either way `.tmp/project/` is deleted on the way out, and `.tmp/` with it when nothing else is in it. |
| `npm run test` | Runs `test:unit` then `test:e2e`. Since the e2e run deliberately leaves a dev server up, this is a local command; never wire it into CI. |
| `npm run test:unit` | Fast `node:test` unit tests (via `tsx`) for the pure modules: the JSX runtime, the bundler, the HTML formatter, the tag parser, page planning, config loading (the `skrapa` key, comments and trailing commas, and every problem that stops a command), the `init` helpers (run against the real template), the `fix` migrations, and the shell rewrites (`applyTagAttrs` and `rewriteShellImports`, the latter against a throwaway temp tree since it reads and writes real files). Some suites also run the freshly built CLI against throwaway projects under `.tmp/` (see `src/scripts/fixture.ts`), each deleted when its suite finishes, and `.tmp/` with the last of them. Plus sync checks: that `template/skrapa.d.ts` is byte-identical to the root `skrapa.d.ts` (the source of truth; nothing copies it, so that test is what holds them together), that the `skrapa` keys in `template/src/tsconfig.json` and `web/tsconfig.json` are valid, and that the committed `web/assets/sitemap.xml` lists exactly the pages under `web/`. No server, so it's the one CI runs. |
| `npm run test:e2e` | End-to-end test (`src/scripts/test.ts`): scaffolds a fresh project from `template/` into `.tmp/project/` (a subdirectory, so the unit-test fixtures created beside it under `.tmp/` are never part of that project; it rebuilds the CLI and `npm link`s the checkout itself, and removes the link again on Ctrl+C or when a check fails), starts its dev server from `.tmp/project/src/` on port 8080, and verifies the site: every template file landed, and the `about/` page picks up its own `index.html`/CSS/`client.ts` instead of the shared shell's. Leaves the dev server running on completion so the scaffolded site can be poked at manually; Ctrl+C stops it and deletes `.tmp/project/` (a failed check does both at once). |
| `npm run lint` / `lint:fix` / `lint:css` | ESLint (with `eslint-plugin-prettier`, so it flags and `--fix`es formatting too) and Stylelint for the CSS in `web/` and `template/`. Prettier otherwise runs on save; there is no standalone `format` script. |
| `npm run clean` | Removes all build output: `dist`, `bin`, `.tmp` and `.skrapa` at the repo root, plus `web/.skrapa`, `template/dist` and `template/.skrapa`. |
| `npm run release` | Runs `commit-and-tag-version` (version bump + CHANGELOG + commit + tag), rebuilds, and pushes with `--follow-tags`. It does **not** publish, and you should not normally run it: `.github/workflows/release.yml` runs it for every commit that lands on `main`, then publishes that tag to npm and deploys the site from it. |

## Releasing

Push to `main`. `release.yml` lints, tests and builds, cuts the version from your conventional commits, pushes the tag, publishes it to npm (`publish.yml`), and deploys the docs site from that tag (`skrapa-pages.yml`). Each step runs only if the one before it passed, so a failing build never becomes a version and a version that never reached the registry never becomes a deploy.

Publishing uses [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) over OIDC, so there is no `NPM_TOKEN` anywhere. Two consequences worth knowing:

- npm validates the OIDC claim of the *calling* workflow, not the one that runs `npm publish`, and allows one trusted publisher per package. The publisher is configured against `release.yml`, which is why `publish.yml` is `workflow_call`-only: a run starting anywhere else could not authenticate.
- `npm publish` from a laptop is refused by a `prepublishOnly` guard (`src/scripts/publish-guard.ts`), since it would publish a working tree under a version with no tag behind it. `SKRAPA_LOCAL_PUBLISH=1` overrides it for a registry outage.

To publish a tag that already exists (a run that failed for a reason unrelated to the code), run the **Release** workflow from the Actions tab with its `tag` input filled in: it skips cutting a new version and publishes that one.

## Notes for the CLI itself

`bin/index.js` is a single bundled file on purpose. `package.json`'s `files` field ships only `bin/`, `template/` and `skrapa.d.ts`, so the CLI can't `require` sibling compiled modules the way `.skrapa/src/bin/*.js` does during development. `src/bin/bundle.ts` is a small CommonJS-style bundler that walks the `require(...)` graph from a compiled entry file and inlines everything reachable under its own directory; anything it can't resolve there (Node builtins, npm packages, files outside that directory) is left as a literal `require(...)` call, which falls through to the real `require` of wherever the bundle ends up running. `cmd-build.ts` reuses the same bundler for a project's client-side `<script src="...ts">` tags, walking the skrapa root's `.skrapa/` instead.
